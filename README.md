## 它解决什么问题

在深圳租房，大家比价时只看**标价租金**。但真实成本是：

```
真实月成本 = 租金 + 通勤时间成本 + 交通费
```

「多花 700 块住近 20 分钟」和「省 700 块每天多挤 40 分钟」，哪个划算？没人算得清，因为**通勤时间没有被定价**。

这个工具把它算出来，并额外回答一个更少人问的问题：**这个价格，在你自己的时间价值下，到底值不值。**

## 四个值得单独讲的设计决策

### 1. 时间单价不预设，但输入方式要贴合人

深圳人算工资是**按月**的，让人自己换算时薪是不友好的。所以给了两种输入：

- **填月薪** → 按国家法定月计薪天数换算：`月薪 ÷ 21.75 ÷ 8`
- **填时薪** → 直接用
- **不填** → 只按「租金 + 交通费」排序，同时把「每月要在路上花多少小时」摆在明面上

**为什么不给一个默认时薪？** 因为那是替用户做价值判断。给一个默认值，等于宣称"你的时间值 50 块"，没有任何依据。

### 2. 通勤不用「单程 35 分钟」，用「每月 26 小时」

后者才有冲击力。而且拆成三种方式：

| 方式 | 计算 | 为什么这样 |
|---|---|---|
| 地铁/公交 | 接口返回真实票价与耗时 | 主方案 |
| 驾车 | 早高峰 8:30 与平峰 14:00 各算一次，出**区间** | 区间本身有信息量：波动大的位置通勤不可靠 |
| 骑行 | 自行车耗时 × 0.75 折算电动车 | 标注「近似」，不假装精确 |

地铁**不**分高峰平峰：地铁不受路面拥堵影响，8:30 和 14:00 耗时几乎相同，差别只在拥挤度——那不是耗时能表达的。

### 3. 数据必须验证过才敢用来推荐

政府参考价是 **2022 年度**的，直接拿来用是耍流氓。所以做了对照实验：

用 276 条真实挂牌房源（贝壳，用户本人浏览后保存页面，脚本本地解析、不发起网络请求）与政府参考价对比：

| 类型 | n | 挂牌/参考 比值中位 | **Spearman 秩相关** |
|---|---|---|---|
| **住宅小区** | 16 | **1.045** | **0.943** |
| 商办公寓 | 14 | 0.791 | 0.252 |
| 混在一起 | 32 | 0.923 | 0.772 |

**住宅类的排序几乎完美（0.943），水平只差 4.5%。而商办公寓完全不适用（0.252）——混在一起会把整体拉到 0.772，典型的辛普森悖论。**

所以：排名只用住宅类，商办公寓和产业厂房分别标注、不参与推荐。完整过程见 [docs/validation.md](docs/validation.md)。

### 4. 空间数据不做全量地理编码，做「按需周边搜索」

要给 3635 个小区补坐标，要 3635 次请求、40 分钟以上连续网络。而**一次周边搜索就能换回 25 个带坐标的小区**，5 页覆盖目的地 4 公里内全部候选。

请求量差两个数量级，而且天然只返回"目的地附近"的房子——这正是需求本身。

## 数据来源与口径

| 项 | 内容 |
|---|---|
| 租金 | 深圳市住房和建设局《房屋租赁参考价格》· [查询平台](https://zjj.sz.gov.cn/fwzljgcx/) |
| 覆盖 | 4319 个小区 + 2043 个城中村（去重后入库 2041 个），2022 年度口径 |
| 通勤 | 高德 Web 服务（路径规划 / 周边搜索 / 地理编码） |
| 校准 | 实测挂牌价：住宅类中位比值 1.045，秩相关 0.943 |

**已知局限**（会写进界面）：
- 租金是**参考价不是成交价**，且基准年为 2022；已用实测比值校准，但仍有时效偏差
- 一房一厅面积 43㎡ 来自实测；二房/三房/复式为政府标准面积，标注为 `estimated`
- 每月按 22 个工作日计；通勤不含等车与体力成本
- 坐标覆盖约 81%（`geocode_communities.py` 可按区续跑补全）；未覆盖的小区靠"周边搜索"仍可命中
