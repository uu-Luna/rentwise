# 数据验证报告：政府参考价还能不能用？

> 这份文档回答一个问题：**深圳市住建局 2022 年发布的租赁参考价，在 2026 年还能不能用来做租房推荐？**
>
> 结论先放这里：**能，但只对住宅小区。** 住宅类的价格排序与真实挂牌市场的秩相关是 **0.943**，水平只差 **4.5%**。而商办公寓完全不适用（秩相关 0.252）。

---

## 1. 为什么要做这个验证

政府参考价有两个可能的失效方式：

1. **时效**：数据是 2022 年度的，现在是 2026 年，深圳租金在跌。
2. **口径**：参考价是评估值，不是成交价，可能系统性偏离市场。

如果这两点加起来很严重，整个项目就只能停在"展示历史数据"，不能做"推荐"。
所以在写界面之前，先拿真实挂牌房源对一次。

---

## 2. 数据

| 项 | 内容 |
|---|---|
| 挂牌房源 | **276 条**，来自贝壳租房 10 个区的「整租 · 一居」页面 |
| 采集方式 | 用户本人登录浏览并保存页面（`.mhtml`），脚本本地解析，**不发起任何网络请求** |
| 政府参考价 | 4319 个小区 + 2043 个城中村（住建局公开平台） |
| 对比指标 | 单价（元/㎡·月），避开面积假设带来的误差 |
| 能匹配上的 | 32 条（要求「区 + 小区名」完全一致） |

276 条里只有 32 条能匹配，因为其余是：
- 品牌长租公寓（独栋·XX公寓），不属于任何小区，政府库里没有
- 小区名与政府库写法不一致

**样本不大，但对判断"排序还准不准"已经够用。**

---

## 3. 第一个发现：三类房源必须分开

一开始把 32 条混在一起算，得到：

> 比值中位 0.923，秩相关 0.772 —— 看起来"参考价偏高、排序一般"

但把房源按**物业类型**拆开后，结论完全变了：

| 类型 | n | 挂牌/政府 比值中位 | 比值区间 | 面积中位 | **Spearman** |
|---|---|---|---|---|---|
| **住宅小区** | 16 | **1.045** | 0.84 ~ 1.15 | 42.9㎡ | **0.943** |
| 商办 / 公寓 | 14 | 0.791 | 0.38 ~ 0.98 | 44.0㎡ | 0.252 |
| 混在一起 | 32 | 0.923 | 0.38 ~ 1.15 | 43.0㎡ | 0.772 |

住宅类的秩相关 0.943（n=16 时显著临界值约 0.5），**说明政府参考价对小区之间的相对贵贱判断，几乎完全正确**。

商办公寓只有 0.252，**等于没关系**——因为政府是按住宅口径评估它们的，而这类物业的租金由另一套逻辑（写字楼、服务式公寓）决定。

**这是典型的辛普森悖论：两个群体各自的规律，混在一起就消失了。**

### 处理方式

在 `communities` 表加 `property_type` 字段，按名称规则分成 `residential` / `commercial`：

```
commercial 关键词：公寓|大厦|广场|商厦|商务中心|时代|金融中心|写字楼|SOHO
```

结果：4319 个小区里，**住宅 3681 个，商办公寓 638 个（14.8%）**。

排名默认只用住宅类；商办公寓保留在库里但标注出来，不参与推荐。

> ⚠️ 这是**规则推断，不是政府标注**。会有误判（比如叫「XX公寓」但实际是住宅），
> 所以界面上要显示"按名称推断"，不能当成事实。

---

## 4. 第二个发现：面积假设错了 23%

| | 原假设 | 实测（住宅类中位） | 偏差 |
|---|---|---|---|
| 一房一厅面积 | 35㎡ | **42.9㎡** | **−23%** |

35㎡ 是**城中村政策规定的标准户型面积**，被错误地套用到了商品房上。
深圳商品房的"一房一厅"普遍 43–55㎡，而城中村确实是 35㎡。

这个错误单独就造成 23% 的金额低估，比"数据旧 6%"严重得多。

### 处理方式

`config.py` 的户型面积增加 `area_source` 字段，诚实标注每个数字的来源：

| 户型 | 面积 | 来源 | 说明 |
|---|---|---|---|
| 单间 | 19㎡ | `policy` | 城中村标准户型 |
| **一房一厅** | **43㎡** | `measured` | **实测住宅挂牌中位 42.9㎡（n=16）** |
| 二房一厅 | 60㎡ | `estimated` | 待补样本 |
| 三房及以上 | 85㎡ | `estimated` | 待补样本 |
| 复式 | 80㎡ | `estimated` | 城中村无此户型 |

`estimated` 的户型，界面上允许用户自己改面积。

---

## 5. 第三个发现：不需要按区校准

我原本的计划是用「中国房价行情」的区级租金指数做分区校准，算出南山要乘 1.329。

**这个方案是错的。**

原因：区级倍数 = `行情区均价 ÷ 我们库的区中位单价`，两边**篮子不同**——
行情平台偏商品房挂牌，我们库还含统建楼、商务公寓，分母被拉低，倍数就被放大。

实测住宅类小区的比值只有 **1.045**，说明参考价与市场几乎一致，
根本不需要 30% 级别的调整。

### 处理方式

- **取消**按区校准
- 只保留一个**全局市场修正系数 1.045**（住宅类实测中位），两类房源同乘，保持相对关系不变
- 数据库同时存原值 `monthly_rent` 和校准值 `monthly_rent_adj`，界面上做开关

---

## 6. 最终结论

| 判据 | 门槛 | 实测 | 判定 |
|---|---|---|---|
| 残差中位数 | < 10% | **4.5%** | ✅ 通过 |
| Spearman 秩相关 | > 0.8 | **0.943** | ✅ 通过 |

→ **可以做小区级推荐，不需要降级到街道级。**

前提条件（写进代码了）：
1. 只对 `property_type = residential` 的小区排名
2. 面积用实测值，不用城中村政策面积
3. 商办公寓不参与推荐

---

## 7. 已知局限

1. **样本量小**：住宅类只有 16 条。秩相关 0.943 在 n=16 时显著，但比值中位数（1.045）的置信区间较宽。
2. **物业类型靠名称规则推断**，会有误判。
3. **只验证了一房一厅**。二房/三房/复式用的是 `estimated` 面积，未验证。
4. **挂牌价 ≠ 成交价**。实际成交通常比挂牌低 3–8%，所以本项目输出的金额偏乐观（偏高）。
5. **单一时点**。挂牌数据是 2026 年 11 月的一次快照，不是持续监测。

## 8. 怎么复现

```bash
# 1. 抓政府参考价
python scripts/fetch_reference_prices.py

# 2. 建库（含物业分类、面积换算、原值+校准值）
python scripts/build_db.py

# 3. 解析你自己保存的贝壳页面
#    放在 data/manual/pages/*.mhtml，然后：
python scripts/parse_saved_pages.py --all-rooms

# 4. 跑对比（见 notebooks 或 docs 里的计算过程）
```

已验证的中间结果：

```
住宅类 n=16   比值中位 1.045   Spearman 0.943
商办公寓 n=14  比值中位 0.791   Spearman 0.252
```

>
> 结果发现真正的问题不是过时——住宅类的秩相关有 0.943，水平只差 4.5%。

>

这个叙事同时展示：**主动质疑数据、量化验证、识别混杂因素、发现自己的错误**。
